# 英語対応・配信国追加の判断材料（#39）

> 状態：**案（決定はオーナー）**。この文書は、やる／やらないを決めるための材料と、推奨案。コードは変えていません。
> 調査日：2026-10-06（`main` の `04c3304` 時点）。行数は `grep` による概算です。

## 1. 結論（推奨案）

**今は「やらない」。ただし、下の「やる条件」を 1 つでも満たしたら、i18n の仕組みから着手する。**

理由：

1. **需要の根拠がまだない。** 英語対応の費用は大きく（後述、画面だけで 2〜3 週、食品データまで入れると別プロジェクト）、需要の確認なしに始める理由がない。
2. **画面の翻訳だけでは売れない。** 食品データ（日本食品標準成分表）と AI の指示文が日本食前提なので、英語の画面で日本食しか検索できないアプリになる。英語圏の需要を満たすには、食品データの差し替えが必要で、ここが最大の費用と審査・表示義務の論点になる。
3. **v1.0 は審査・リリース前後の段階。** 国を増やすと、サポート・法務・為替・審査のやり直しが同時に増える。まず日本で、課金とコーチ機能（v1.1）を回して数字を見るほうが安い。
4. **後から入れても、手戻りは小さくできる。** 今のうちにやっておくと安く済むこと（日付・数値・文言を直書きしない新規コードのルール）を、第 6 節に挙げた。これは費用がほぼかからない。

「やる／やらない」は、完了条件のとおり決定が必要なので、**オーナーが第 4 節の基準で決める**。この文書は決定済みの扱いにしない。

### 文言ではなく、データ・仕様に日本語が入っているもの（翻訳より重い）

- **食品データ**：`src/data/foods.json`（日本食品標準成分表（八訂）、2,478 食品、約 180KB）と `src/data/catalog.json`（165 品）。名前は日本語の成分表表記。検索は、かな正規化と日本語の別名辞書（`foodSearch.ts`）に依存している。英語名・英語の検索は、そもそもない。
- **AI の指示文**：`supabase/functions/estimate-meal/prompt.ts` は「日本の食事を読み取る係」と日本語で書かれ、カタログ（日本語名）の key で答えさせる。`catalog.json` も別に持っている。
- **種目名・部位**：`Part = '脚' | '背中' | ...` が型・係数表（`PART_COEF`）・DB の値になっている。表示用の文字列とデータ上の値が同じなので、翻訳する前に「内部の値」と「表示名」を分ける移行が要る（既存ユーザーの端末 DB のデータ移行を含む）。
- **日付・数値の書式**：`toLocaleString('ja-JP')`、`年・歳・日` を文字列に直接つなぐ書き方、`Asia/Tokyo` の既定値が複数ある。
- **ネイティブ側の文言**：`app.json` の HealthKit・カメラ・写真の利用目的の説明文（日本語）。
- **サーバー側**：Edge Function のエラーメッセージ（`index.ts`、`delete-account`）、1 日の上限の数え方（日本時間）。
- **画面の外**：コーチ用 Web（`coach/`、日本語）、`web/legal.html`、`docs/privacy-policy.md` と `docs/terms.md`、App Store の掲載文（`docs/app-store-listing.md`）。
- **お金**：購入画面の `¥3,800`・`¥300/月` が直書き。RevenueCat と App Store Connect の価格は国別に設定できるが、文言と表示は別に直す必要がある。

## 4. 配信国を追加するときの条件

### 4.1 審査（App Store）

- 配信国は App Store Connect の「価格および配信状況」で選ぶ。現在は**日本のみ**（`docs/app-store-listing.md`、`docs/app-review-reply.md` に「日本語のみ・日本のみ」と書いてある）。国を増やすのに、アプリの新しい審査は要らないが、**審査メモ・掲載文の「日本のみ」の記述は書き直す**。
- 言語の追加は、App Store Connect で言語ごとに、名前・サブタイトル・説明・キーワード・スクリーンショットを入れる。英語のメタデータを足すだけでも、検索に出る範囲が変わる。
- 審査員は、英語の画面で操作を確認する。食品検索が日本語しか効かないままだと、「機能しない」と見られる危険がある（第 2 節のとおり）。
- 年齢レーティング・健康関連のガイドライン（食事・ダイエットの表現、数値の根拠の表示）は、国をまたいで同じ基準で見られる。今の「出典の表示」（`citations.ts`）は、そのまま使える。

### 4.2 表示義務・法務

国ごとに、少なくとも次を確認する（**法的な助言ではなく、確認すべき項目の一覧**。国を増やす前に、専門家に確認する）。

| 論点 | 日本（今） | 国を増やすとき |
| --- | --- | --- |
| 事業者情報の表示（特定商取引法） | 日本の表示（`docs/terms.md`、`web/legal.html`） | 国によっては、事業者の住所・連絡先の表示が別に要る。個人事業主の住所の公開が負担になる場合がある |
| 個人情報・プライバシー | 個人情報保護法・Apple のプライバシー表示（`docs/privacy-policy.md`） | EU・英国：GDPR（根拠・権利・越境移転の説明、場合により代理人）。米国：州法（CCPA など）。カナダなど。アプリのデータ送信先（Supabase・AI の提供元・Sentry・RevenueCat）の所在国の説明も更新する |
| 準拠法・管轄 | 日本法・東京地裁（`docs/terms.md`） | 消費者の居住国の強行規定が優先される場合がある。規約に例外の書き方が要る |
| 健康情報・医療機器の扱い | 「目安であり医療ではない」と表示 | 国ごとに、健康・医療の表現の規制が違う（FDA・EU の規制など）。表現を保守的にする。HealthKit の利用目的の文言は英語版が要る |
| 栄養成分の表示・出典 | 文部科学省「日本食品標準成分表（八訂）」の出典を表示（`docs/release-checklist.md`） | 使うデータの利用条件に合わせた出典の表示（USDA なら、その規約に従う） |
| 課金・消費税 | 価格は日本円（Apple の価格表）。インボイス・消費税は日本の扱い | Apple の価格表で国別に価格を設定でき、税の徴収は Apple が行う。ただし、**Apple 経由でない請求（コーチ用 Web など）を国外で行うなら、別の検討**。為替で価格がずれるため、定期的に見直す |
| サポート | 日本語で対応 | 英語の問い合わせに答えられる体制と、対応の目安の時間 |

### 4.3 食品データの日本向けの偏り

- 成分表は**日本の食品・料理**中心。外国の食品（ブランド品、レストランの料理、サプリ・プロテイン、冷凍食品など）はほぼない。筋トレ層は、プロテインやパッケージ食品の記録が多いので、英語圏では**バーコード検索・ブランド食品**の需要が大きい。今のアプリにはこれがない。
- 食品の名前・別名辞書は、日本語（かな・漢字）専用で、英語の検索（複数形・綴りの揺れ・ブランド名）には使えない。
- 1 食の量の単位（`grams` に換算するプロンプトの指示：「2個」「1杯」）が、日本の食習慣前提。英語圏では cup・oz・serving などが要る。
- 身長・体重の単位は、今は cm・kg 固定。米国では ft/in・lb が必要になる。
- AI の指示文と評価ケース（`eval/`）は日本食のみ。英語圏の食事（皿・サンドイッチ・ファストフード・外食）の精度と費用は、**未測定**。

## 5. 判断基準

### やる条件（1 つでも満たしたら、A から着手する）

次の「需要の証拠」のうち、**1 つ以上**が出たら進める。

1. **ユーザーからの声**：英語版・海外からの利用の要望が、1 か月に **5 件以上**（レビュー・問い合わせ・SNS・コーチ経由）。
2. **日本国内の英語話者の利用**：端末の言語が英語の利用者が、全体の **10% 以上**（App Store Connect の App Analytics の言語別。配信が日本のみなので、海外の実績は見えない。海外の需要は、次の項目の事前登録で確かめる）。
3. **待ちリストの調査**：英語の LP（`web/index.html` の英語版）や SNS で、メールの事前登録を試して、**100 人以上**が集まる（広告費を使う場合は、上限を先に決める）。
4. **日本での成長が頭打ち**：日本での有料の人数が、合計 **500 人**を超え、かつ前の 3 か月の伸びが止まっている（国内の見込みが尽きた）。
5. **提携**：英語圏のコーチ・パートナーから、利用の具体的な申し出がある。

加えて、**着手の前提**として、次がそろっていること。

- 日本での課金が回っている（課金の動作確認・審査が済み、v1.1 が出ている）。
- 月 1 回のメンテナンス（`docs/monthly-maintenance.md`）が回り、サポートに余裕がある。
- 追加費用（翻訳・AI の増加・法務の確認・サポートの時間）を、収益で賄える見込みがある。

### やらない条件（次のどれかなら、見送る）

- 上の「需要の証拠」が、**どれも出ていない**（今はこの状態）。
- 日本の有料ユーザーが少なく、**国内の改善（記録の速さ・食品データの充実・AI の精度）のほうが、1 時間あたりの効果が大きい**。
- 個人の事業主として、**海外向けの法務（GDPR・住所の表示など）を負担できない**、またはその確認のための費用が、見込める収益を上回る。
- 英語圏向けの食品データ（C2）に、数週間の時間を割けない。「画面だけ英語」は、価値が低いので選ばない。
- 英語のサポートを続ける体制がない。

### 段階の進め方（やると決めた場合）

1. **A（i18n の仕組み）**を先に入れる。日本語のまま出して、挙動が変わらないことをテストで確かめる。→ これだけで、いつでも英語を足せる状態にする。
2. **小さく試す**：日本に住む英語話者向けに、**日本食のまま英語の画面（C1）**を出して反応を見る。配信国は日本のままで、**法務の負担がほとんど増えない**。
3. 反応が良ければ、**米国のみ**を追加する（C2：USDA）。他の国は、その結果を見て決める。EU・英国は、GDPR の対応が重いので最後にする。

## 6. 今からできる、費用のほとんどかからない準備

- 新しい画面・コンポーネントでは、**日付・数値・単位の書式を、共通の関数を通す**（既存の `fmt` が画面ごとに重複している。1 か所にまとめる）。これは日本向けの改善にもなる。
- 新しい文言は、**1 つの画面の中で、定数にまとめて書く**（あとでキーに移しやすくする）。
- `Part`（部位）のように、**表示名をそのまま保存する値**を新しく作らない（`id` と表示名を分ける）。
- 食品データは、`id`（`01001` など）で参照し、名前に依存した処理を増やさない。
