# 月曜のまとめ通知に「ひとこと」を添える：push 通知の設計案（issue #33）

コーチが書いた「ひとこと」が届いたことを、通知で気づけるようにする。いまは、アプリ内のカードと今日画面の 1 行だけ。サーバーからの push が要るので、方式・許可・プライバシー・導入の順番を比べる。

> **ステータス：すべて「案」。** コードは変えていない。方式や運用の決定は人間が行う。決めてほしいことは §9 に並べた。
>
> 根拠は、コードと SQL を読んで確認した（`src/services/notifications.ts`、`src/components/NotificationPrompt.tsx`、`supabase/migrations/20260929120000_coach_mode.sql`、`app.json`）。Expo の仕様は、SDK 57 の versioned docs（`https://docs.expo.dev/versions/v57.0.0/sdk/notifications/`）と Push の送信ドキュメントで確認した。

---

## 1. 結論（推奨）

| 項目 | 推奨 |
|---|---|
| 方式 | **Expo Push Service**（端末は Expo の push トークンを取り、Supabase の Edge Function が Expo の API へ送る） |
| 送るもの | 「コーチからひとことが届いています」だけ。**ひとこと本文は push に載せない**（本文は、アプリを開いたときに今まで通り `my_coach_inbox()` で取る） |
| 送る数 | ひとことが書かれたときに、**1 週に最大 1 通**。夜間は避けて、次の朝 8 時（端末の時刻）に送る |
| 許可 | 今ある許可（`NotificationPrompt`）を **そのまま使う**。許可ダイアログを増やさない。コーチとつながっていて、許可済みのときだけ、トークンをサーバーに登録する |
| 導入 | 3 段階（§8）。**段階 0 は、コードを変えずにできる確認だけ**。段階 1 は 1 つの開発ビルドで、コーチ 1 人・生徒 1 人から試す |

理由：
- すでに `expo-notifications` が入っていて、`app.json` にもプラグインがある。追加のネイティブ部品は、**ほぼ要らない**（§4）。
- 送る相手が少ない（1 人のコーチにつながれる生徒は 100 人まで）ので、Expo の送信上限（1 秒 600 通）に当たらない。
- 外部サービスは増えるが、**Expo は v1.0 から使っている**（EAS・OTA 更新）。新しい事業者を増やさずに済む。
- 本文を載せなければ、健康に関わる文面が Apple・Expo のサーバーを通らない（§5）。

## 2. いまの通知（確認した事実）

| 事項 | 内容 | 根拠 |
|---|---|---|
| 通知の種類 | 端末内の**ローカル通知 2 種類だけ**：トレーニング後「あとP・C」、月曜 8:00「先週のまとめができました」（毎週くり返し） | `notifications.ts` |
| 許可の取り方 | **初めてトレーニングを完了した直後に 1 回だけ**、説明の画面（`NotificationPrompt`）を出してから iOS の許可ダイアログ。「あとで」なら設定からオンにできる | `NotificationPrompt.tsx` |
| 方針の文言 | 「トレーニングの後と、週のはじめだけ届きます。記録を催促する通知は送りません」。App Store の説明にも「毎日の記録を催促する通知は送りません」とある | `NotificationPrompt.tsx`、`app-store-listing.md` |
| サーバー送信 | **なし**。push トークンの取得もしていない | `notifications.ts` |
| ひとことの流れ | コーチが `send_note()`（RPC）で `coach_notes` に書く → 生徒のアプリが起動・復帰したときに `my_coach_inbox()` で取る。**書かれたことを生徒に知らせる仕組みはない** | SQL |
| ひとことの上限 | 本文 500 字まで、コーチ × 生徒 × 週で 1 件（同じ週に書き直すと上書き） | `coach_notes` の制約、`send_note()` |

つまり今の月曜 8:00 の通知は、**ひとことがあってもなくても同じ文言**で鳴る。ひとことの有無は、アプリを開くまで分からない。

## 3. 方式の比較

| | A. 今のまま（ローカル通知だけ） | **B. Expo Push（推奨）** | C. APNs を直接 | D. FCM / OneSignal など |
|---|---|---|---|---|
| ひとことが書かれたことを知らせられる | いいえ（月曜 8:00 の固定文言のみ） | はい | はい | はい |
| 端末側の追加 | なし | トークン取得（`getExpoPushTokenAsync`） | ネイティブのデバイストークン取得（`getDevicePushTokenAsync`） | SDK の追加（ネイティブ、重い） |
| サーバー側の追加 | なし | Edge Function 1 つ + 表 1 つ | Edge Function + APNs の認証キー（.p8）での JWT 署名と HTTP/2 | 各社の設定 + Edge Function |
| 新しい事業者 | なし | なし（Expo は既に利用） | なし（Apple のみ） | あり（プライバシー表示と規約が増える） |
| Android | — | 同じコードで可（FCM の設定は別途） | **別実装が要る** | 可 |
| 失敗の扱い | — | レシートで「登録切れ（`DeviceNotRegistered`）」が分かる | 自分で APNs の応答を処理 | 各社による |
| 実装の重さ | なし | 小〜中 | 中〜大 | 大 |
| 向いている場面 | 通知を増やしたくない | **少人数・iOS 中心・早く出したい** | Expo をやめたくなったとき | 通知が主力機能になったとき |

補足：
- **A の改良案（サーバー不要）**：コーチとつながっているときだけ、月曜の文言を「先週のまとめと、コーチのひとこと」に変える。ただし、ひとこと**が書かれたか**は分からないまま。ひとことが無い週に「ひとこと」と鳴ると、嘘になる。完了条件（「ひとことが届いたことが通知で分かる」）を満たさない。
- iOS のバックグラウンド取得で、起動前にひとことを取ってローカル通知にする案もある。iOS は実行のタイミングを保証しないので、「届いたことが分かる」の確実さが足りない。採らない。
- C は Expo の仕組みを自分で作り直すことになる。Expo Push は、APNs へ送るところまでを引き受けてくれる。将来、Expo をやめるときに移ればよい（トークンの表の形は同じ考え方で足りる）。

## 4. 必要な追加（B の場合）

### 4-1. アプリ側

| 事項 | 内容 |
|---|---|
| パッケージ | **`expo-notifications`（`~57.0.21`）は `package.json` に既にある**。`app.json` の `plugins` にも `"expo-notifications"` がある。新しい npm パッケージは要らない見込み |
| 新しいビルドは要るか | **要る可能性が高い。** iOS の push 用の権限（`aps-environment`）は、ビルドに焼き込まれる。いま端末にある開発ビルド・v1.0 のビルドに入っているかは、**コードからは断定できない**（§9 の確認事項）。入っていなければ、OTA 更新では足りず、**新しいネイティブビルド**（`eas build`）と審査が要る。TestFlight で確かめる |
| トークンの取得 | `getExpoPushTokenAsync({ projectId })`。`projectId` は `app.json` の `extra.eas.projectId`（設定済み）。ネットワークが無いと失敗するので、失敗は静かに無視して次の起動で再試行する |
| Expo Go | 開発中は **開発ビルドで確認する**（Expo Go は、Android では SDK 53 から remote push が使えない。iOS でも本番と同じ経路の確認には開発ビルドが確実） |
| Android | PLATE は iOS 向け（Sign in with Apple、HealthKit）。Android に出すなら、FCM の資格情報と通知チャンネルの設定が別に要る。**今回は対象外** |

### 4-2. APNs のキー

- Expo Push で iOS に送るには、**Apple Developer の APNs 認証キー（.p8）を EAS に登録**する（EAS が管理する資格情報。`eas credentials` またはビルド時の案内で作れる）。キーは Apple のアカウントで作り、Expo のサーバーが APNs に送るために保持する。
- App ID（`app.plate.pfc`）で Push Notifications の capability が有効になっている必要がある。EAS Build は通常、capability を自動で同期する。
- **人間の作業**：Apple Developer アカウントでのキー作成と承認、EAS への登録は、アカウントの持ち主が行う。**この作業ではしない**（Secrets・外部サービスの本番変更にあたる）。
- キーは失効しない設計だが、**失効・再作成したら全端末への送信が止まる**ので、`docs/monthly-maintenance.md` の点検に「push が届くか」を足す（§9）。

### 4-3. サーバー側（Supabase）

| 部品 | 案 |
|---|---|
| 表 `push_tokens` | `user_id`、`token`、`platform`、`tz`（端末のタイムゾーン、例 `Asia/Tokyo`）、`updated_at`。`user_id` は `auth.users` を参照して **`on delete cascade`**（アカウント削除で一緒に消える。既存の表と同じ） |
| 書き込み | 他の表と同じく **RPC 経由**（`register_push_token(token, tz)`、`unregister_push_token(token)`）。表そのものは RLS で本人だけ・読み取りも本人だけ。コーチには見せない |
| 送る処理 | Edge Function `send-coach-note-push`。**サービスロールのキーはここだけ**で使う。Expo の API（`https://exp.host/--/api/v2/push/send`、1 回に 100 件まで）へ POST。応答（またはレシート）が `DeviceNotRegistered` ならトークンを消す |
| きっかけ | 候補は 2 つ。(1) `coach_notes` への INSERT/UPDATE を **Database Webhook** で Edge Function に渡す。(2) 予約済みの行を **GitHub Actions の cron**（`supabase-keepalive.yml` と同じ仕組み）で 1 時間おきに拾う。**夜間を避けて次の朝 8 時に送る**には、(2) の形（`push_outbox` のような表に「送る時刻」を置く）が素直 |
| Expo の送信の保護 | EAS の「アクセストークンを必須にする」設定をオンにし、トークンは Supabase の Secrets に置く（登録は人間） |
| 費用 | Expo Push の料金は、公式ドキュメントに書かれていない（確認できていない）。この規模（生徒数 × 週 1 通）なら、通常は問題にならない見込みだが、**Expo のダッシュボードで確認してから**進める |

## 5. push トークンの保存とプライバシー

| 論点 | 案 |
|---|---|
| トークンは個人情報か | 端末と紐づく識別子。**ログインしたユーザーの ID と紐づけて保存する**ので、「識別子」として扱い、プライバシーポリシーに書く |
| 何を載せるか | 通知の文面は固定（「コーチからひとことが届いています」）。**ひとこと本文・生徒の名前・数値は載せない**。通知は Apple・Expo のサーバーを通るので、健康に関わる内容は載せない方針 |
| コーチ名を載せるか | 載せない案を推す（「コーチ」だけ）。名前を載せたほうが親しみは出るが、通知の文面は端末のロック画面に出る。出したければ、生徒が決められる設定にする（段階 2 以降） |
| 保存期間 | `unregister_push_token()`（通知をオフにしたとき、コーチとの共有をやめたとき）で削除。アカウント削除は `on delete cascade`。`DeviceNotRegistered` のときも削除 |
| 誰が読めるか | 本人と、Edge Function（サービスロール）だけ。コーチには見せない |
| コーチとの共有をやめたら | `revoke_my_link()` のあと、**ひとことは届かない**ので、トークンの登録も不要。`revoke_my_link()` で一緒に消すか、送る処理が「有効なつながり」を条件にする（後者で十分、前者なら二重に安全） |
| 一時停止（「ひとりで」） | `paused` の間は送らない。ひとことは書けるが、通知しない（コーチから見える挙動は変わらない） |
| App のプライバシー（栄養表示ラベル） | 「**デバイス ID**」を、**アプリの機能**の目的で、**ユーザに紐づく：はい**で足す案。トラッキング（ATT）には当たらない（広告や他社データとの突き合わせをしない）。最終的な回答は App Store Connect の質問文を読んで人間が決める |
| ポリシー・規約 | `docs/privacy-policy.md` の「1. 取得する情報」「3. 第三者への提供・委託」に、push 通知のためのトークンの取得と、Expo（Expo Push Service）・Apple（APNs）への委託を足す案。**このファイルでは反映しない**（`docs/v1.1-review-prep.md` と同じ理由：人間の最終確認のあとに反映） |
| 審査メモ | `docs/v1.1-review-prep.md` §5 の「通知」の行と、審査メモ（「通知は増えない」の文）を見直す。**「オンにしない限り…通知は増えず」は、push を入れたあとも成り立つように、コーチ機能をオンにしていない人には push のトークンを登録しない**ようにする |

## 6. 許可の取り方

今の `NotificationPrompt` は、**初めてトレーニングを完了した直後**に、「トレーニングの後と、週のはじめだけ届きます」と説明してから iOS のダイアログを出す。これを土台にする。

| 場面 | 案 |
|---|---|
| すでに許可済みの人 | 新しい許可ダイアログは**出さない**。コーチとつながったとき（`accept_invite` が成功したとき）に、トークンをサーバーへ登録するだけ。**iOS の許可は「通知」1 つで、ローカルも push も同じ**ため、許可し直しは要らない |
| まだ聞いていない人 | コーチとつながった直後の画面に、**説明つきの 1 画面**を出す案：「コーチのひとことが届いたら、お知らせします。ひとことが無い週は、通知しません」。ボタンは「通知をオンにする」「あとで」（既存の `NotificationPrompt` と同じ作り）。**接続前には聞かない**（理由がまだ無いため） |
| 拒否した人 | 何もしない。しつこく聞かない。設定の「通知」から、オンにできる。アプリ内のカードは今まで通り |
| 設定画面 | 「コーチのひとこと」の通知のオン／オフを 1 つ。オフにしたら `unregister_push_token()` |
| 文面の見本 | 「コーチからひとことが届いています」（タイトル：PLATE）。見本は説明の画面にも出す（今の `NotificationPreview` と同じ） |

## 7. 「催促しない」方針との整合

方針は、「**記録を催促する通知は送らない**」。ひとこと通知は、コーチが書いたことへの**お知らせ**で、記録の催促ではない。ただ、通知が増えることには違いないので、次の決まりを守る。

| 決まり | 内容 |
|---|---|
| 送る条件 | **ひとことが書かれたとき**だけ。ひとことが無い週は、何も送らない（今の月曜 8:00 のローカル通知を除く） |
| 送る数 | 1 人につき **1 週に最大 1 通**（`coach_notes` の同じ週の書き直しでは、再送しない） |
| 送らないもの | 「記録がありません」「目標まで○」「コーチが待っています」のような、**行動を促す文面**。コーチ→生徒の通知に、記録の有無を使わない |
| 時間 | 夜間に鳴らさない。次の朝 8 時（端末の時刻）まで待つ |
| 止め方 | 設定でいつでもオフ。iOS の通知設定でオフにしても、アプリは動く |
| 文言 | ポリシーの文言は、「トレーニングの後と、週のはじめだけ届きます」→「**コーチのひとこと**」を足して改める（説明の画面、App Store の説明文とも） |

**月曜 8:00 に 2 通鳴る問題（決めてほしい点）：** いまの月曜のローカル通知は固定文言で、コーチとつながった人にも鳴る。ひとこと通知が同じ朝 8 時に重なると、2 通になる。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| (a) 重ねる | ローカルはそのまま。ひとこと通知は別に鳴る | 実装が最も小さい | 月曜の朝に 2 通 |
| **(b) ひとこと通知を 9:00 にずらす（推奨の初期案）** | ローカルの 8:00 のあと、書かれていれば 9:00 に 1 通 | 重ならず、文面で区別できる | 2 通には違いない |
| (c) 統合する | コーチとつながっていて push が登録できた人は、ローカルの月曜通知を**取り消し**、サーバーから月曜 8:00 に 1 通だけ送る（ひとことがあれば文面を変える） | 1 通だけになる。「ひとこと」の有無で嘘にならない | サーバー送信に失敗すると、まとめの通知も届かない。ローカルの再登録の処理が要る。段階 2 以降の話 |

→ 段階 1 は **(b)**、運用して問題が無ければ段階 2 で **(c)** を検討する、を推す。

## 9. 決めてほしいこと・人間の作業

### 決めること

1. **push を v1.1 に入れるか、v1.2 以降にするか。** 入れるなら、v1.1 のビルドに含める（審査 1 回）。後にするなら、v1.1 は今のローカル通知のままで出せる（推奨は、**まず v1.1 を出し、push は v1.2**。理由：ひとことの機能が実際に使われるかを見てから、通知を足すほうが、「通知を増やさない」方針に沿う）。
2. 方式は Expo Push でよいか（§3）。
3. 月曜 8:00 の重なり（§7）は (a)(b)(c) のどれにするか。
4. 通知にコーチ名を載せるか（推奨：載せない）。
5. 通知の文面：「コーチからひとことが届いています」でよいか。

### 人間の作業

- Apple Developer：APNs 認証キーの作成、App ID の Push Notifications の確認。
- EAS：キーの登録、送信のアクセストークンの設定。Expo の費用・上限の確認。
- Supabase：新しい migration の適用、Edge Function のデプロイ、Secrets の登録（本番の変更なので、この作業ではしない）。
- App Store Connect：栄養表示ラベルに「デバイス ID」を足す（§5）。
- `docs/privacy-policy.md` / `docs/terms.md` / `web/legal.html` の反映（人間の最終確認のあと）。
- `docs/monthly-maintenance.md`：「push が届くか」の点検を足す。

## 10. 確認の方法（実装するときに使う）

1. 開発ビルド（`eas build --profile development`）を、実機の iPhone に入れる。シミュレーターでは push トークンを取れない。
2. 2 つのアカウント（コーチ・生徒）でつなぐ。許可を出し、`push_tokens` に 1 行できたことを確認する。
3. コーチで `send_note` を実行 → 次の朝 8 時（検証では、送る時刻を手で今に変えて）に、通知が届くか確認する。
4. 通知をタップして、アプリが開き、ひとこと（今日画面の 1 行・カード）が見えるか確認する。
