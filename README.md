# PLATE

トレ連動PFCアプリ。「今日のトレで、今日の一皿が決まる。」
筋トレ記録とPFC管理を1本にまとめ、トレの内容に合わせて毎日の食事目標が自動で変わる iOS アプリ（Expo / React Native）。

仕様の正は設計書（`design_handoff_plate/spec/トレ連動PFCアプリ 設計書.pdf`）。UI とブランドは `design_handoff_plate/README.md` と試作HTML。

## 開発

```bash
npm install
npx expo start          # 実機は Expo Go。HealthKit・課金は開発ビルドが必要（下記）
npm run web             # Web でプレビュー（http://localhost:8080。確認用で、本番の対象は iOS）
npm test                # ドメインのテスト
npm run typecheck
```

- **Web プレビューは `npm run web` で起動する。** Web 版の SQLite は SharedArrayBuffer が必要で、ページ本体に COOP/COEP ヘッダーが要る。Expo の開発サーバーは HTML にそれを付けられないので、`scripts/web-dev.mjs` が付けて中継する。
- 開発ビルド: `npx eas-cli build --profile development --platform ios`（実機）または `development-simulator`。HealthKit・RevenueCat・Apple サインインは Expo Go では動かない。
- 環境変数は `.env.example` を `.env.local` にコピーして埋める。**どれも未設定でも動く**（課金・ログイン・AI は無効になり、AI入力は成分表との照合で推定する）。

## 設計書との対応

**できているもの**
- 目標エンジン（式1〜5）：プロフィール→TDEE（Mifflin-St Jeor×活動係数）→週合計、日タイプ配分、PFC分解、週内の再配分（±10%で止める）。摂取実績の過不足も残りの日に配る。3週目以降は直近14日の実データでTDEEを補正（前回値との加重平均）。極端な減量の警告（1%/週・基礎代謝の下限）。
- 端末内SQLite（Drizzle）に、設計書のテーブルと、全テーブルの id(UUID)・updated_at・deleted_at。`day_target` に再配分の履歴、`meal_entry` に記録時の値のスナップショット。
- 成分表（全2,478品目）の検索。「鶏むね」「ごはん」など日常の言い方の別名辞書つき。マイ食品、成分表示からの手入力。
- 食事記録：マイセット（時間帯の候補が上、最近使った順）／検索／**AI（写真・文章）**、AI推定の確認画面（写真のサムネイル・ひとこと・「写真から推定」のタグ）、AIの印、1日の回数上限（写真と文章の合計）。
  - 今日タブの**カメラボタン**：押すとすぐカメラが開き、撮ったら、食事シートのAIの画面を写真つきで開く。写真で記録した食事は、リストに28pxのサムネイルが出る（写真はアプリ内に保存し、`meal_entry.photo_uri` に入る。`input_type` は set／search／text／photo）。
  - **確認画面で、AIの推定が違っていても直せる**：行ごとにgの±、「食品を変える」（別の食品に差し替え。量は引き継ぐ）、「削除」、下の「＋ 食品を追加」（成分表・マイ食品から選ぶ）。「見つからず」の行も「食品を選ぶ」で解決できる。手で選んだ行には「手動で選択」のタグが付く。
  - 写真の推定は、画像を読めるモデルに写真とひとことを送り、食品ごとの{名前, g}だけを返させる。**PFCは成分表の値から計算する**（AIに直接PFCを出させない）。AIの設定がないときは、写真は推定できない（文章だけ成分表と照合する）。
- トレ記録（v2）：メニュー（テンプレート）の編集、約80種目＋別名検索（BSS・RDL・OHP など）、前回値と「+2.5kg」、セット追加、種目追加（一覧にない名前はその場で作れる）、フリートレ、休憩タイマー、履歴。完了画面の「あとP・F・C」と、日タイプが変わったときの再配分の通知。1日に複数回のトレーニングは、ボリュームを合わせて日タイプを決める。「続きを記録」で、完了を取り消して再開できる。
- 過去の日も編集できる：今日タブで日付を選ぶと、その日の食事の追加・修正（時間帯・量）・削除と、体重の記録ができる。‹ › で前の週にもさかのぼれる（最大52週）。食事を直すと、その週の残りの日の目標も再計算される。過去のトレの内容の編集は未対応（履歴からの削除のみ）。
- **体重**（design_handoff_plate の README どおり）：
  - 7日平均は、その日から過去7日の記録の平均（記録がない日は飛ばす）。**Pの計算に使う体重も7日平均**。
  - ペース = （今日の7日平均 − 14日前の7日平均）÷ 2。到達予測 = （7日平均 − 目標）÷ ペース。
  - 今日タブの体重の行（未入力は「今朝の体重」＋前回の値＋黒い「入力」、入力済みは「変更」）、体重入力シート（日付の切り替え・入れ忘れた日の追加と修正・削除、記録も削除も取消できる）。
  - レビューの体重カード（7日平均・先週との差・直近28日・「直近2週 −0.2kg/週（予定 −0.5）」）と、体重の詳細（1か月／3か月／全期間、目標線・今のペースの見込み・「今日」の線、到達予測、直近30日の記録）。
  - **ペースの見直し（v2で画面からは外した。自己管理できる人が対象のため。関数 `suggestPace` とテストは残してある）**：7日平均の2週間の減り方が予定より0.15kg/週以上遅く、1週前の窓も遅い（増量は逆）と、「週の合計を◯kcal減らしますか？」を出す。**量は遅れに応じて変わる**（遅れ × 7700 × 0.5 を100単位に丸め、300〜1,400kcal/週）。**直近14日に食事を記録した日が10日未満なら出さない**。**維持カロリーを補正した週・見直しを受け入れた週から14日は出さない**（二重に絞らない）。**計画どおり食べていないとき（減量で目標の5%超の食べ過ぎ／増量で5%超の食べ足りない）も出さない**（原因が食事なので）。減量で、週の合計が基礎代謝×7日を割るほどの提案はしない。勝手には変えず、「そのまま」か「週 −◯kcal にする」を選ぶ（README の固定700kcalとは違う）。変えたら取消つき。1回答えたら次の週まで出さない（`pace_suggestion`）。受け入れた分は、設定の「週の合計」に反映され、そこから元に戻せる。
  - 目標体重（設定で±0.5kg）。
- Apple ヘルスケア：体重を自動で取り込むスイッチと、いま取り込むボタン（設定。コードのみで未検証）。
- 週次レビュー（v2）：直近4週のトレーニングのカレンダー（色は日タイプ）と、押した日の内容、体重カード、平均PFC。推定1RM・1RMグラフ・ペースの見直し・「先週は目標より+800kcal」は出さない。無料は直近2週。
- 設定（v2の順）：アカウント → プロフィール（性別・生まれた年・身長・体重は7日平均から自動・活動量 低い1.4／ふつう1.6／高い1.85・基礎代謝・維持カロリー。変えると目標がすぐ変わる）→ 目標 → いつもの食事（朝・昼・夜のマイセット）→ 日ごとの食べる量 → たんぱく質 → 週間スケジュール → 食事・ヘルスケア・プラン → ログアウト（一番下。「この端末の記録も消す」スイッチつき）。アカウント（ログイン中はメール・「Appleでログイン中・バックアップ 今日 6:02」・「同期済み」、ログアウト中は「ログインしてバックアップ」→Appleのシート、ログアウトの確認シート）、目標（目的・目標体重・ペース・週の合計）、**日ごとの食べる量**（「差を小さく／標準／差を大きく」から選ぶだけ。高い日・通常の日・オフの日の kcal を棒と数字で見せる。「細かく調整」で「高い日 +15%」のように%で変える）、たんぱく質（「体重1kgあたり 2.2g → 1日 158g」）、週間スケジュール、マイ食品。内部では日タイプ係数（設計書の m）に対応する。
- 体験中／購入済み／見るだけ（体験後に未購入）の機能差、4週間の無料体験、CSV書き出し、データ削除、ダークモード。
- ログイン画面（`design_handoff_plate 2` の案11c）：Apple／「ログインせずに始める」。起動画面（`assets/splash-login.png`）からそのまま続いて見える。ログインせずに始めても全機能をローカルで使え、あとから設定で「ログイン」できる。ログイン済みで別端末にバックアップがあれば、オンボーディングで復元できる。

**設定が要る・未検証のもの**（コードはあるが、鍵・アカウント・実機がないので動作確認していない）
- **Supabase**（ログイン・バックアップ）：`supabase/migrations/` の内容を適用し（単独の新規プロジェクトなら `supabase db push`、既存プロジェクトに相乗りするなら SQL Editor に貼って実行。理由は `docs/release-checklist.md` B章）、`.env.local` に URL とキーを入れる。ログイン方法ごとの設定：

- **AI入力**：`supabase/functions/estimate-meal` をデプロイ（`GEMINI_API_KEY` を secrets に）。1日30回の上限はサーバー側で止める。無料の3回は端末側で数えている（無料／有料のサーバー判定には RevenueCat の webhook が要る。未対応）。原価の実測は未実施（設計書の未決事項）。

## 既知の点
- Web 版でグラフ用ライブラリが出す開発用の警告（`Unknown event handler property`）は、Web の開発画面では非表示にしている。ネイティブでは出ない。
- 週間スケジュールの日タイプは、テンプレートの既定値。個別の日だけ変えたいときは、トレタブの「予定を変える」「今日は休む」を使う。
- 開発ビルドでは、データ画面に「サンプルデータを入れる（3週間分）」、初回のオンボーディングに「サンプルデータで始める」が出る（本番ビルドには出ない）。体重21日・食事14日・トレ21日分で、実際の食品とグラム、食べ過ぎ／軽い日／記録なしの日、AI入力の食事、予定を飛ばした日・予定外にやった日を含む。入れる前に、既存の記録は消える（設定・プロフィールは残る）。
- **サンプルデータの自動投入（開発用）**：`.env.local` に `EXPO_PUBLIC_AUTO_SAMPLE=1` を入れて起動すると、初回だけ、ログインとオンボーディングを飛ばしてサンプルつきで始める（すでに始めているときは、記録をサンプルに置き換える）。入れたあとは印を残し、記録を消しても勝手には戻さない。`.env.local` は git に入らない。環境変数を変えたら、`npx expo start -c` で起動し直す。サンプルには、写真で記録した食事（サムネイルの確認用）も含む。
- 起動画面の全画面表示は、Expo の `enableFullScreenImage_legacy`（将来なくなる予定の指定）を使っている。

## デザインシステムの運用
- 色・余白・フォントは `src/design-system/tokens.ts` にだけ書く。画面に色コードを直書きしない（ライト／ダークで切り替わる）。
- ストアなどアプリのロジックに依存する部品は `src/components/` に置き、デザインシステムには入れない。

| `src/store/coachStore.ts` | コーチの状態（kv に小さく保存）。`useIsManaged()`・`isManagedNow()` で「コーチが設定」の見るだけ制御 |
| `src/app/(coach)/` | コーチのタブ（生徒 / メニュー / 設定）と、生徒の詳細・目標を変える・メニュー編集。ルート名は `(tabs)` と重ならないようにしてある |
| `src/app/coach-join.tsx`・`coach-link.tsx` | 生徒側：招待コード → 承認、見せる項目・ひとこと・共有をやめる |
| `coach/` | Web 管理画面（Next.js）。同じ RPC と `src/features/coach` の集計をそのまま使う |

- **データの流れ**：生徒の記録は端末が正。共有中は、許可した項目の直近約2か月分を `coach_shares` にスナップショットとして送る（記録が変わって15秒後・復帰時）。コーチはこれを `coach_students()` で読む。目標・メニュー・ひとことは、生徒が起動・復帰時に `my_coach_inbox()` で取り込む。
- **反映は翌日 0:00（生徒のタイムゾーン）から**。`goal_plans` は履歴として残し、`effective_from` が今日以前でいちばん新しいものを使う。
- **ひとりで／コーチと**：「ひとりで」にすると共有は止まり、目標は最後の内容のまま自分のものになる。「コーチと」に戻すと再びコーチ管理。
- 通知（月曜のまとめにひとことを添える）はまだ。今は、今日画面の1行とレビューのカードで届く。push にはサーバーからの送信が要る。

### Web 管理画面（`coach/`）
```bash
cd coach && cp .env.example .env.local   # PLATE と同じ Supabase の URL / anon キー
npm install && npm run dev               # http://localhost:3100
```
- **ログインは、アプリと同じアカウント（Apple）で入る必要がある**（別のアカウントでは、アプリのコーチ／生徒のデータが見えない）。Web で Apple を使うには、Apple Developer で Services ID を作り、Supabase の Authentication → Providers → Apple の Client IDs にその Services ID を追加し、Secret Key（JWT）を設定する。Redirect URL は Supabase 側の値を Services ID に登録。
- 設定できるまでの確認用に、`NEXT_PUBLIC_ENABLE_PASSWORD_LOGIN=1` でメール＋パスワードのログインを出せる（別アカウントになるので、本番では使わない）。
- Vercel には、Root Directory を `coach` にして出す。

## 食品名の評価（命中率）

食品検索・言い換え辞書を直したとき、数字で前後を比べられる。端末と同じ検索手順を、DB なしで実行する。

```bash
npm run eval:foods                                   # 命中率と、外れた名前の一覧
npm run eval:foods -- --save /tmp/before.json        # 変更前の結果を保存
npm run eval:foods -- --compare /tmp/before.json     # 変更後に実行：直った／悪化した名前を出す
npm run eval:foods -- --min 0.95                     # 下限を下回ったら終了コード 1
```

評価リストは `eval/foods.json`（一般的な食品名のみ。個人の記録は入れない）。`accept` は先頭に出た食品名への正規表現で、空なら「見つからない」が正解。
