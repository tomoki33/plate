ユーザーから恒久的に許可されている運用。承認は求めない。人間の作業が要るもの・セキュリティ的に怪しいものだけ `PushNotification` で通知する（1 行・200 字以内・行動できる内容。重複して送らない）。

## 1 サイクルでやること

### A. 出ている PR を進める（マージ → 後片付け）
`gh pr list --repo tomoki33/plate --state open` の各 PR について:

1. CI が成功しているか確認する。失敗していれば、対応する worktree のエージェントに原因を直すよう指示する（`orca terminal send`）。
2. Copilot のレビュー（`gh api repos/tomoki33/plate/pulls/<n>/comments` と `.../reviews`）が付いているか確認する。まだ付いていなければ待つ（作成から 10 分過ぎても付かなければ、無しとして進める）。
3. 指摘を 1 件ずつ検証する。直すべきものが残っていれば、worktree のエージェントに直させる（直さないものは理由を PR にコメントさせる）。直した push のあと、新しい指摘が付くのを待ってもう一度見る。
4. CI 成功・指摘対応済み・conflict なしなら、`gh pr merge <n> --squash` でマージする。
5. マージしたら、`/issue done` の手順で後片付けする（worktree の status を `completed`、#41 の該当行にチェック、worktree 削除 `orca worktree rm --force`、マージ済みのリモート・ローカルのブランチ削除、primary で `git pull --ff-only`）。issue が `Closes #N` で閉じていなければ `gh issue close`。
6. 数件マージしたら、primary で `npm ci && npx tsc --noEmit && npx vitest run` を回し、main が壊れていないか確認する。壊れていたら、直す worktree を作る。

### B. 空きがあれば次の issue に着手する
進行中（`in-progress` / `in-review`）の worktree が 4 本未満なら、#41 の上から順に、チェックが付いていない issue を選ぶ。

- 着手できる: コードで完結する、または大半がコードで完結するもの。人間が必要な部分は手順をまとめるだけでよい（エージェントには自分でやらせない）。
- 並行して触るファイルが重なるものは、同時に着手しない。依存する issue（例: #14 は #12 の結果が前提）は、前提が済むまで着手しない。
- 着手は `/issue` の手順に従う（primary を最新の main にし、`--base-branch origin/main --no-parent`、status を `in-progress`）。

### C. 通知するもの（`PushNotification`）
次の場合だけ、自分では実行せずに通知する。内容は「何をしてほしいか」を先頭に。

- 人間の作業が必要: ダッシュボード操作、外部アカウントの作成・契約・課金、Secrets の登録、Supabase 本番へのデプロイやマイグレーション適用（権限で止まる）、実機での確認、本人の同意が要るもの。
- セキュリティ的に怪しい: 秘密情報がコミットされている、権限を広げる変更、不審な依存の追加、Copilot がセキュリティ上の指摘をしていて直せないもの。
- 自分では解決できない失敗: CI が直らない、conflict が解けない、エージェントが止まって戻らない。
- 着手できる issue がすべてなくなった（完了の報告）。

人間の作業待ちの issue は、手順を `docs/` か PR 本文に残し、#41 のチェックは付けずに次へ進む。同じ内容は 2 回通知しない（通知したものはこの会話のメモに残す）。

### D. 終わりの判断
着手できる issue が残っていて、進行中の PR もあるなら、次のサイクルを予約する。何も動いていない（待ちが人間の作業だけ）なら、通知してサイクルを止める。

## やってはいけないこと
- 本番（Supabase・Google Cloud・App Store 等）の変更、Secrets の書き込み。権限で止まるが、迂回しない。
- ユーザーのデータや記録を、リポジトリに置く。
- 指摘を検証せずにマージする。
